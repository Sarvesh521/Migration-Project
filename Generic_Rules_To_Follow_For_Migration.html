Generic Rules for MongoDB to MySQL Schema & Data Migration

Can the Conversion Be Rule-Based, and Where Does It Need a Human?

Summary

Yes — a substantial part of MongoDB→MySQL schema conversion can be reduced to generic, reusable rules, but not all of it. Structural and type-level transformations can be automated by sampling documents and statistically inferring a schema. What can’t be automated is anything depending on intent — whether a value that looks like a foreign key actually is one, or whether a nested object deserves its own table. Every rule below is tagged:

  • Fully automatable
  • Automatable with review (confident heuristic, can still be wrong)
  • Requires domain input (cannot be safely automated)

Evidence this is feasible: a peer-reviewed method (Aftab et al., Automatic NoSQL to Relational Database Transformation with Dynamic Schema Mapping, Scientific Programming, 2020) built and benchmarked a fully automatic MongoDB→MySQL/PostgreSQL pipeline that infers schema dynamically and outperformed Talend on the same task. Commercial/open-source tools (Hackolade, Variety, mongo-jsonschema) already do sampling-based schema inference in production — Hackolade specifically infers implicit relationships by testing whether ObjectId values resolve to documents in another collection, and has a “suggest normalization” mode for relational targets. The consistent pattern: structure/type inference is automatable from data; semantic interpretation is not.

Core Rules

1. Collection → Table. Each collection becomes one table, name normalized to snake_case. Fully automatable. Merging two collections that represent the same entity under different names (schema-drift symptom) is domain input.

2. BSON Type → MySQL Type. Fixed lookup table, always choosing the type that preserves precision:

BSON Type MySQL Type Why
ObjectId CHAR(24) or BINARY(12) Preserves the identifier as-is
String VARCHAR(n) / TEXT Length from observed max during sampling
Int32 / Int64 INT / BIGINT Match bit-width; never downcast Long→INT
Decimal128 DECIMAL(M,D) — never FLOAT/DOUBLE Built for precision (e.g., money); floats lose it silently
Boolean TINYINT(1) —
Date DATETIME(6), normalized to UTC Captures ms/µs precision, avoids timezone drift
BinData VARBINARY / BLOB —
Array / Object Child table (see Rule 4) Not a scalar type

Scalar mapping: fully automatable. Choosing column width from sampled data: automatable with review (sample may miss the true max).

3. _id → Primary Key. Default ObjectId case: fully automatable (CHAR(24)). Heterogeneous _id types within one collection (legal but unusual in MongoDB) require detecting the type union during sampling and defaulting to a canonical string form — requires domain input to confirm, since it changes sort/index behavior.

4. Nested Objects & Arrays → Relational Structures. The largest source of judgment calls:

Structure Rule Status
Shallow embedded object, always present Flatten to prefixed columns (address_city) Automatable with review
Deeply nested / contains arrays Extract to child table + FK Automatable with review (extraction trigger can be auto-thresholded)
Array of primitives Junction table or JSON column Requires domain input — depends on query pattern, not shape
Array of objects Always a child table, never flattened Automatable with review — close to a safe universal rule (1NF)
Arrays/documents near the 16MB BSON limit Force child-table extraction; batch-insert for fan-out Fully automatable as a guardrail (flag above a size/length threshold)

General principle: automate “must normalize” as a hard rule for repeating objects; leave “flatten vs. JSON” as an overridable default for shallow data.

5. Primary Key / Foreign Key Identification. Two heuristics, both producing suggestions, not certainties: - Naming convention (xId → collection x): cheap, imprecise — false positives and negatives both occur. - Value-matching: sample ObjectId-typed fields and test resolution against candidate collections (Hackolade’s technique); a high hit-rate (e.g., >95%) is strong evidence.

Status: automatable with review. Before creating an actual MySQL FOREIGN KEY, validate the relationship against the full dataset (not the sample) for orphaned references — MongoDB never enforced these, so broken references are common.

6. Null/Missing Fields & Type Inconsistency. - Absent vs. null vs. empty: track field presence rate during sampling; if <100%, column is nullable. Mapping “absent”→NULL is fully automatable; deciding whether the app needs to distinguish absent/null/empty (requiring an extra flag column) is domain input. - Mixed types in one field: apply a type-widening hierarchy — Null < Boolean < Integer < BigInt < Decimal/Double < Date < String — falling back to VARCHAR/JSON only when no common numeric/date type exists (the same approach used by Delta Lake/Databricks schema evolution). Fully automatable as a default policy. Reviewing why a field widened to text (possible legacy bug) is a data-quality judgment call.

Additional Rules Worth Adding

  • Sparse/partial uniqueness: MySQL has no native sparse-unique index; use a generated column + unique index, or app-level enforcement. Flag as a manual reconciliation item.
  • Schema drift over time: take the union of all historically observed field names, not just recent documents, to avoid the common failure of recency-biased sampling. Merging field-name variants (phone vs. contact.phone) needs a person to confirm.
  • “Overflow” catch-all column: route long-tail rare fields into a single extra_fields JSON column rather than dozens of sparse columns; the frequency threshold is configurable, not absolute.
  • Prefer an existing $jsonSchema validator over statistical inference when a collection has one — it’s authoritative, not a guess.
  • Validate constraints against the full dataset, not the sample, before enforcing NOT NULL/UNIQUE/FOREIGN KEY — a failed ALTER TABLE late in migration is expensive to debug.

Recommended Process

  1. Sample and infer per collection using a statistically sound method ($sample), not “first N documents.”
  2. Apply fixed automatable rules to produce a first-draft schema and type mapping.
  3. Run review-tier heuristics (FK detection, nesting thresholds, nullability, overflow thresholds) to produce a candidate, confidence-scored schema.
  4. Surface every domain-input item as an explicit human checklist before finalizing.
  5. Validate the finalized schema against the full dataset before enforcing constraints.
  6. Re-run inference periodically for collections still receiving writes during a live/CDC migration.
